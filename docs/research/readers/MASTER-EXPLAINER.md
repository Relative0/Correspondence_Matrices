## Domains

Boolean logic is the arithmetic of yes and no. It looks trivial in isolation — an AND, an OR, a NOT — and becomes hard the moment you have thousands of them wired together and need a guaranteed answer about all of their combinations at once. That situation is far more common than it sounds.

### Plain-language explanation

A Boolean expression is a rule built from conditions that are each either true or false: *this user is an admin AND the account is not suspended*. Evaluating it once, for one specific case, is easy. The hard questions are about *all possible cases*: is there any combination of inputs that lets this through? Do these two rules always agree? Which condition is actually doing the work?

Those questions are hard because the number of combinations doubles with every condition you add. Twenty conditions is a million cases; forty is a trillion. Every field below has some version of this problem, and each has built its own tools for it.

### Technical detail

Each domain below is a place where the central object is a Boolean function over a set of variables and the question of interest is a property of the whole function rather than a single evaluation: satisfiability, equivalence, implicant structure, reachability, or minimal representation. The representations differ; the underlying algebra does not.

These are candidate application domains for a structural layer, not validated deployments of this one. No result on this site was measured on a workload from any of them apart from the EPFL circuits, which sit under formal verification and hardware synthesis.

### AI reasoning and neuro-symbolic systems

#### Question

Given everything the model has concluded so far, is this next step even consistent?

#### Plain-language explanation

Systems that mix learned prediction with hard rules need a way to check that a proposed answer does not violate the rules — and to do it fast enough to sit inside a reasoning loop.

#### Technical detail

Constraint propagation and consistency checking over a symbolic knowledge layer, typically with heavy reuse of the same constraint set across many candidate assignments.

#### Lay name

AI that mixes learning with hard rules

### Formal verification and EDA

#### Question

Are these two circuits the same circuit?

#### Plain-language explanation

Before a chip design is manufactured, engineers must prove that the optimised version computes exactly the same thing as the original — for every possible input, not just the ones they tested.

#### Technical detail

Combinational equivalence checking, model checking, and property verification. This is the domain that produced BDDs, and the one the external validation on this site draws its circuits from.

#### Lay name

Chip design and verification

### Constraint solving and SAT

#### Question

Is there any way to satisfy all of these requirements at once?

#### Plain-language explanation

Scheduling, planning, packing, routing: enormous numbers of interlocking yes/no choices where you need one workable combination, or proof that none exists.

#### Technical detail

Boolean satisfiability over CNF, with modern conflict-driven clause-learning solvers. The question is existential rather than exhaustive, which is why SAT scales to problems where explicit enumeration cannot.

#### Lay name

Scheduling, planning and packing

### Hardware design and synthesis

#### Question

What is the smallest set of gates that computes this function?

#### Plain-language explanation

Turning a description of what a circuit should do into an actual arrangement of gates, using as little silicon and power as possible.

#### Technical detail

Logic synthesis, technology mapping, and two-level or multi-level minimisation. Representation choice directly determines what optimisations are even expressible.

#### Lay name

Turning designs into circuits

### Rule engines and decision systems

#### Question

Which rule fired, and why?

#### Plain-language explanation

Insurance pricing, credit decisions, benefits eligibility, medical triage protocols: large bodies of business rules that must produce an explainable decision and must not contradict each other.

#### Technical detail

Decision tables and rule networks where the operational needs are conflict detection, redundancy elimination, coverage analysis, and traceable attribution of an outcome to a rule.

#### Lay name

Business rules and automated decisions

### Security policy and access control

#### Question

Can any user reach this resource by some path we did not intend?

#### Plain-language explanation

Permission systems are Boolean expressions over roles, attributes and context. The dangerous question is not what a policy does allow but what it accidentally allows.

#### Technical detail

Policy analysis over role and attribute predicates: reachability, privilege-escalation search, policy-difference computation between two versions, and change-impact analysis.

#### Lay name

Permissions and access control

### Configuration and feature flags

#### Question

Is this combination of settings even reachable, and what does it do?

#### Plain-language explanation

A product with forty independent switches has more than a trillion possible configurations. Teams need to know which combinations are valid, which are dead, and what a new flag interacts with.

#### Technical detail

Configuration-space analysis over feature models: dead-feature detection, constraint consistency, and repeated evaluation of the same predicate under many different flag assignments.

#### Lay name

Product settings and feature switches

### Computational biology and Boolean networks

#### Question

Which stable states can this regulatory network settle into?

#### Plain-language explanation

Gene regulation can be modelled as switches turning each other on and off. Researchers want the long-run states the system falls into, and what perturbations move it between them.

#### Technical detail

Boolean network dynamics: attractor identification, basin-of-attraction analysis, and control-target search over networks of Boolean update functions.

#### Lay name

Gene networks in biology

### Knowledge graphs and ontologies

#### Question

Does this new fact contradict anything already asserted?

#### Plain-language explanation

Structured knowledge bases carry rules about what can and cannot be true together. Adding facts means re-checking consistency, constantly.

#### Technical detail

Consistency and subsumption checking over description-logic constraints, where the same constraint structure is re-queried under many different partial assignments.

#### Lay name

Structured knowledge bases

### Compiler optimisation and program analysis

#### Question

Can this branch ever be taken?

#### Plain-language explanation

Compilers reason about which conditions can hold at each point in a program, so they can delete impossible branches and prove that a rewrite is safe.

#### Technical detail

Path-condition reasoning, dataflow analysis, and reachability over predicates — with repeated partial evaluation of the same condition under evolving context, which is exactly the reuse pattern a compiled structural representation would target.

#### Lay name

Compilers analysing your code

## Use cases

Where Correspondence Matrices might create distinctive value

CM is most interesting when a Boolean function is not a disposable answer but a long-lived object: it must retain useful structure, survive across sessions or versions, accept transformations, and answer related questions repeatedly. The cases below are reasoned application hypotheses, not claims of deployed advantage.

### Evidence boundary

Hardware/formal-verification expressions and bounded real feature-model slices have been tested. Neither establishes deployed-workflow advantage, and the feature-model performance comparisons retain documented measurement gaps. Every other field below remains a candidate whose CM-specific benefit needs a real trace and a direct incumbent comparison.

### Advantages

#### Retain structure, not only an answer

A flat truth vector answers what the function does. A CM can also retain operator and subexpression organization, so a later tool can inspect, transform, compare, or attribute parts of the computation instead of reconstructing them from output alone.

#### Reuse a compiled identity

Expression keys, serialization, process-local compiled caching, and operator transforms are implemented. That creates a route to reuse across evaluations and related analyses, although durable production value has not yet been demonstrated.

#### Change the context without discarding the object

Restrictions and partial evaluation can keep the stable part of a model while inputs, policies, interventions, or versions change. Synthetic context tests improved over uncached CM but did not establish an advantage over incumbent engines.

#### Keep exactness and provenance together

Where complete explicit output is feasible, CM can couple an exact result with the structure that produced it. The output still grows exponentially with semantic support, so this is a bounded capability rather than an unlimited replacement for SAT or decision diagrams.

### Hardware verification and electronic design

#### Status

Measured adjacency

#### Problem

Engineers repeatedly prove that optimized circuits preserve behavior, inspect logic cones, and assess the effect of design revisions.

#### How CMs could help

A reusable expression identity plus retained operator structure could link equivalent outputs back to the subcircuits that produced them, support structural difference between revisions, and avoid rebuilding unchanged logic for every related check.

#### Information retained

The function, its semantic support, operator composition, reusable subexpressions, and version lineage can remain attached to one artifact rather than being reduced to a one-off answer vector.

#### Incumbents and alternatives

AIGs, ROBDD/CUDD, SAT/SMT, equivalence checkers, and synthesis tools already dominate this field. CM would need to complement them at an artifact or workflow boundary, not merely duplicate their core query.

#### Evidence still needed

Replay a real design history and show lower total workflow cost or clearer change attribution against the incumbent representation.

### Artificial intelligence with hard rules

#### Status

High-value hypothesis

#### Problem

Agents and neuro-symbolic systems may reuse the same safety rules, permissions, or consistency constraints across many proposed actions and rapidly changing contexts.

#### How CMs could help

CM could compile the hard-rule layer once, retain which predicates and operators produced a decision, restrict it under each new context, and compare rule-set versions without treating every check as a fresh expression.

#### Information retained

Rule identity, composition, support, transformations, and decision provenance can survive alongside exact Boolean behavior; the learned model itself is not represented by the CM.

#### Incumbents and alternatives

SAT/SMT, policy engines, Datalog, knowledge-graph reasoners, and ordinary compiled predicates may be better for existence queries or mature production integration.

#### Evidence still needed

Use a real guardrail or agent-policy trace to measure reuse, update frequency, explanation needs, and end-to-end cost against the deployed rules engine.

### Computational biology and Boolean regulatory networks

#### Status

Research hypothesis

#### Problem

Boolean gene and signaling networks are repeatedly evaluated under knockouts, interventions, initial conditions, and model revisions while researchers track stable states and causal structure.

#### How CMs could help

A structured, reusable artifact could preserve each update rule and its dependencies, reuse unchanged network regions, and apply restrictions for interventions without flattening away the regulatory composition.

#### Information retained

Update-function lineage, shared regulatory modules, intervention context, and exact bounded behavior can stay connected, which may help compare model versions and explain changed attractors.

#### Incumbents and alternatives

BDD-based attractor tools, SAT methods, graph algorithms, and specialized Boolean-network packages already exploit domain structure and may scale much further.

#### Evidence still needed

Benchmark real published networks on attractor or intervention workflows, including memory and repeated-query cost, against specialized BDD/SAT tools.

### Quantum-computing support logic

#### Status

Narrow research hypothesis

#### Problem

Quantum workflows contain classical Boolean subproblems: reversible-oracle logic, circuit-control conditions, syndrome predicates, and equivalence checks on compiled Boolean components.

#### How CMs could help

For those Boolean boundaries, CM could retain the construction of a predicate or reversible logic component, reuse compiled substructure across circuit revisions, and expose structural differences that a flat classical truth table loses.

#### Information retained

Classical predicate structure and provenance may be preserved. Quantum amplitudes, phase, entanglement, and general unitary evolution are outside the CM claim.

#### Incumbents and alternatives

Quantum decision diagrams, ZX-calculus tools, SAT/SMT, reversible-logic synthesis, and circuit-specific equivalence systems target the genuinely quantum or reversible parts directly.

#### Evidence still needed

Choose one Boolean boundary in a real quantum toolchain and compare correctness, artifact reuse, change analysis, and total cost with the native representation.

### Compilers and program analysis

#### Status

High-value hypothesis

#### Problem

Compilers revisit path conditions, guards, and optimization predicates as program context evolves across passes and source revisions.

#### How CMs could help

CM could retain predicate construction, share repeated subexpressions, partially evaluate under known facts, and carry stable identity through transformations or incremental builds.

#### Information retained

The relationship between a result, its source predicate, its support, and the transformations already applied need not be discarded after one evaluation.

#### Incumbents and alternatives

SSA-based dataflow, e-graphs, BDDs, SAT/SMT, abstract interpretation, and compiler-native memoization already solve overlapping pieces.

#### Evidence still needed

Instrument a real compiler or analyzer and test whether repeated predicates and context changes repay CM preparation against its native incremental machinery.

### Security policy and access control

#### Status

High-value hypothesis

#### Problem

Long-lived policies are evaluated repeatedly, revised frequently, and audited for accidental reachability, privilege escalation, and change impact.

#### How CMs could help

A CM artifact could keep policy clauses and composition attached to exact behavior, reuse unchanged structure, restrict under user or environment attributes, and compare versions structurally.

#### Information retained

### Configuration systems and product families

#### Problem

Feature models and configuration rules persist across releases while teams test many related contexts and ask what a changed flag can affect.

#### How CMs could help

Persistent expression identity, serialization, structural difference, and partial evaluation align with a workload made of related rule versions and many incomplete assignments.

#### Information retained

#### Incumbents and alternatives

### Regulated rule and decision systems

#### Status

Auditability hypothesis

#### Problem

Eligibility, pricing, triage, and compliance systems need repeatable decisions, controlled rule changes, contradiction checks, and explanations tied to the exact rule version.

#### How CMs could help

CM could serve as a versioned structural artifact whose exact Boolean behavior, rule composition, transformations, and reuse history remain available to evaluation and audit tools.

#### Information retained

The decision function and how it was assembled can stay together, reducing the information loss that occurs when a rule set becomes only generated executable code or isolated outcomes.

#### Incumbents and alternatives

Decision tables, business-rule engines, DMN tooling, SAT/SMT, and conventional audit logs may already provide the required governance more simply.

#### Evidence still needed

Test a real governed rule lifecycle and compare traceability, change review, contradiction detection, and operating cost with the incumbent system.

### When to consider CMs

#### Good fit

The same Boolean structure is evaluated, restricted, transformed, or compared many times.

Operator or subexpression lineage matters after the first answer is produced.

Version differences and partial contexts are first-class workflow objects.

The semantic support is bounded enough for the required explicit artifact, or the CM is used as a structural layer rather than forced to enumerate everything.

#### Poor fit

The job is a one-off complete evaluation where BitSet's low setup cost dominates.

The only question is whether one satisfying assignment exists; SAT is built for that.

A canonical symbolic graph under a fixed variable order is the required artifact; ROBDD/CUDD already supplies it.

The workload needs general quantum-state, numeric, probabilistic, or continuous computation rather than a Boolean structural layer.

## Toolbox

Each tool below is excellent at the thing it was built for and mediocre or irrelevant at the others. There is no honest single speed ranking across them, because they do not produce the same thing.

### Plain-language explanation

Compare a calculator, a spreadsheet, and a proof. All three deal with numbers. Asking which is *fastest* is a malformed question — they produce different outputs and answer different questions. The Boolean toolbox is in the same position.

The useful question is not “which is best?” but “what am I actually asking for?” If you want a specific answer, you want something that computes it. If you want a guarantee that covers every case at once, you want something that reduces the rule to a standard shape, or a solver. If you want the smallest circuit, you want a minimiser.

### Technical detail

Grouped by role: **execution kernels** produce an explicit output vector over the semantic support (BitSet, the CM packed path, compiled evaluators). **Symbolic engines** produce a graph or normal form that supports post-construction queries (ROBDD/CUDD, SAT, SymPy). **Minimisers** produce a smaller equivalent expression (Espresso).

A comparison is only meaningful within a role, and only when both sides produced the same artifact — which is why every timed comparison in this project is gated on bit-for-bit output equality first, and why construction and evaluation costs are never merged into one ranking.

### Tools

#### BitSet (packed explicit evaluation)

##### Role

execution kernel

##### Question

What is the complete answer table for this expression?

##### Superpower

Almost no overhead. It packs many input combinations into machine words and evaluates them all in parallel with ordinary bitwise instructions. Nothing to build, nothing to look up.

##### Cost

The output is exponential in the number of variables that matter. It has no reusable structure — ask again tomorrow and it does the same work again.

##### Analogy

A very fast pocket calculator. No setup, no memory, brilliant for one-off sums.

##### Measured

The fastest end-to-end path at every semantic support measured here, from 7.8× faster at live_k=4 down to 1.40× at the guard limit.

##### Lay name

BitSet

##### Lay role

the no-setup calculator

##### Lay question

What is the answer for every possible combination of inputs?

#### ROBDD / CUDD

##### Role

symbolic engine · canonical form

##### Question

Are these two functions the same? Can I query this function repeatedly without re-deriving it?

##### Superpower

Reduces a function to a canonical graph. Under a fixed variable order, two functions are identical exactly when their graphs are identical — so equivalence becomes a pointer comparison.

##### Cost

The graph's size depends heavily on the variable ordering, and finding a good order is a search with a real price. Pulling an explicit answer table back out is expensive, because it means walking the graph once per combination.

##### Analogy

A well-organised index. Expensive to build and sensitive to how you sort it, but then any lookup is instant.

##### Measured

Built the whole corpus in 2.49 ms–2.58 ms into graphs of 78 nodes or fewer — while full extraction of the explicit vector ran 74×–12,782× slower than the packed kernels.

##### Lay name

CUDD

##### Lay role

the compressed index

##### Lay question

Are these two rules the same — and can I keep asking questions about one of them cheaply?

#### SAT solver

##### Role

symbolic engine · existential search

##### Question

Is there any assignment that satisfies all of this?

##### Superpower

Finds one satisfying answer, or proves none exists, on problems with millions of clauses — without ever enumerating the space.

##### Cost

Answers an existence question, not an enumeration question. It will not hand you the full answer table, and counting solutions is a different and much harder problem.

##### Analogy

A search party. Superb at finding one thing in an enormous space; the wrong tool for mapping the whole space.

##### Measured

Not benchmarked in this project. It answers a different question from anything measured here, and no comparison against it is claimed.

##### Lay name

A SAT solver

##### Lay role

the search party

##### Lay question

Is there any combination at all that satisfies all of this?

#### Espresso

##### Role

minimiser

##### Question

What is the smallest two-level form of this function?

##### Superpower

Heuristic minimisation that reliably produces compact sum-of-products covers, which is what a hardware synthesis flow wants next.

##### Cost

Optimises expression size, not evaluation speed, and targets a specific two-level form rather than arbitrary structure.

##### Analogy

An editor who cuts your draft in half without changing what it says.

##### Measured

Not benchmarked in this project. It optimises a different objective from anything measured here.

##### Lay role

the editor

##### Lay question

What is the shortest way to write this rule?

#### SymPy (symbolic algebra)

##### Role

symbolic engine · rewriting

##### Question

Can I manipulate this expression algebraically — simplify it, substitute into it, transform it?

##### Superpower

General-purpose symbolic manipulation with a very wide vocabulary of transformations, well beyond Boolean logic.

##### Cost

Generality has a price. It is not built for packed evaluation and is orders of magnitude off the pace of a dedicated kernel on that task.

##### Analogy

A full mathematics workbench. Everything is possible; nothing is optimised for one job.

##### Measured

Not benchmarked in this project.

##### Lay name

SymPy

##### Lay role

the maths workbench

##### Lay question

Can I rearrange this expression the way I would rearrange algebra on paper?

#### Structural CSE (+ sharing-aware flattening)

##### Role

execution kernel · the honest baseline

##### Question

If I compile this expression to a shared graph and evaluate that, how fast is it?

##### Superpower

Identifies repeated subexpressions, computes each once, and — with sharing-aware flattening — collapses chains of the same operator into single wide operations without duplicating shared work.

##### Cost

Preparation is not free, and the compiled program only pays off if you evaluate it more than once.

##### Analogy

Doing your working out on paper once and then reading off the answers, instead of redoing the arithmetic each time.

##### Measured

This is the baseline the whole project is measured against. Against a plain CSE with no flattening, CM runs about 11% faster. Against sharing-aware CSE-flat, B1/E3 and EPFL measured parity, while current B2/B4 V3 measured bare CM at 0.8906 overall and 0.9612 at k=16.

##### Lay name

A compiled evaluator

##### Lay role

the working-out-once approach

##### Lay question

If I do the working-out once and keep it, how fast is it after that?

#### CM (Correspondence Matrices)

##### Role

structural representation and compilation layer

##### Question

What operator produced this? How is it structured? Can it be transformed, decomposed, cached, or matched against another?

##### Superpower

Treats the operator itself as the object. It gives every expression a canonical key, keeps a persistent compiled cache, serialises, and knows which variables actually matter before it evaluates anything.

##### Cost

Compilation costs roughly 4.1×–4.4× what the CSE baseline's does, and the end-to-end call carries 50.3 µs–91.1 µs of fixed overhead. Both must be amortised by reuse.

##### Analogy

A build system rather than a compiler. The value is in knowing what you already built and being able to reuse it — not in the raw speed of any single build.

##### Measured

Workload-dependent against CSE-flat: parity on B1/E3 and EPFL, but a modest bare-program advantage on current B2/B4 V3. ## What is cm

A Correspondence Matrix represents a Boolean operator as an ordered binary matrix. The point is not that it computes a different answer — it computes exactly the same answer — but that it makes a different set of operations expressible.

### Truth table

#### Plain-language explanation

A truth table answers *what are the outputs?* You list every combination of inputs and write down what comes out. It is complete, and for a fixed variable ordering it pins the function down exactly.

A Correspondence Matrix answers a different question: *what operator produced those outputs, and what is its structure?* Same function, same answers — but now the operator is an object you can hold, compare, decompose, and store.

#### Technical detail

A complete truth function, a normalised CM, and a reduced ordered BDD can each identify a Boolean function under their respective conventions. Their organisation and their supported operations differ. Uniqueness of a CM is relative to an ordered variable basis; matrix equality requires the same normalised ordered basis on both sides.

This is the same distinction as between a list of a function's values and a closed-form expression for it. Both determine the function; only one supports algebraic manipulation.

### Live k

#### Plain-language explanation

Here is the single most important idea for reading any chart on this site. Suppose a system has 32 variables available, and you write the expression `x2 AND x17`.

Two variables matter. The other thirty do not appear and cannot change the answer. The meaningful output is four rows — every combination of two variables. The *ambient* truth table over all 32 variables has 4,294,967,296 rows, but 4,294,967,292 of them are copies of those same four answers.

So the honest measure of how big a job is is not how many variables exist. It is how many variables *actually change the answer*. This project calls that number `live_k`, and it is the horizontal axis of essentially every chart here.

#### Technical detail

Nominal *n* is the size of the variable namespace. Syntactically used variables are those appearing in the expression. Semantic support, `live_k`, counts variables with a genuine functional effect — a variable can appear syntactically and still be semantically dead, as in `x AND (y OR NOT y)`.

Explicit output size is 2<sup>live_k</sup>, not 2<sup>n</sup>. Plotting against nominal *n* without qualifying semantic support silently compares shallow sparse formulas against dense all-live ones and produces curves that mean nothing.

This is not a modelling assumption; it was measured. Holding `live_k` fixed and varying the ambient namespace across 16, 20, 24 moves the measured ratio by 0.040.

### Operator calculus

Representing an operator as a matrix makes a family of operations expressible that a truth table does not naturally support. It is important to be exact about which of those are implemented, which exist in the formalism but have never been demonstrated on a workload, and which are neither.

#### Plain-language explanation

Once the operator is an object rather than a list of answers, you can ask things like: what is the difference between these two rules? Can this rule be factored into simpler ones? What does it reduce to if I fix one input?

The formalism supports those questions. That is a genuine and separate claim from “we have implemented them and shown they pay off,” and this project has been careful not to blur the two.

### I need to evaluate one expression, once.

#### N

01

#### Verdict

Use BitSet

#### Verdict why

there is no setup to spread across

#### Plain-language explanation

If you are going to ask a question once and then move on, you want the tool with the least setup. BitSet has essentially none: it loads many input combinations side by side into the chunks of memory the processor works in, and works out all their answers in a single pass.

CM has to compile the expression first, look it up in its store of already-compiled work, plug in your inputs, and read the result back out. All of that is real work, and if you only evaluate once there is nothing to spread it across. At the smallest problems the setup costs several times more than the actual computation.

#### Technical detail

The measured end-to-end ratio favours BitSet at every semantic support tested, from 7.8× at live_k=4 to 1.40× at live_k=16 — and that is the cached case, where the CM program is already compiled. Uncached in a warm environment the ratio runs 3.6×–4.3×.

The gap is fixed overhead, not kernel speed: 50.3 µs–91.1 µs of binding, environment setup, cache lookup and extraction per call. Because it is roughly constant, it shrinks in relative terms as the useful work grows — at live_k=16 the bare BitSet call is already 156.9 µs against a CM call of 211.3 µs — but it does not vanish below the guard limit.

The corresponding pre-repair claim that CM was modestly ahead at controlled live_k 12 and 16 does not survive this measurement. It is listed in the corrections ledger and appears nowhere else on this site.

### I need to evaluate the same expression thousands of times.

#### N

02

#### Verdict

It depends entirely on how many times — and you should measure that first

#### Verdict why

reuse count is the decision variable

#### Plain-language explanation

Now the calculus changes. Compilation is a one-time cost, and each evaluation afterwards is slightly cheaper. So there is some number of evaluations at which compiling pays for itself. Below it you lose; above it you win.

That break-even number is the single most useful thing to know about your workload. Against a plain, unflattened baseline the typical synthetic expression needs about 78 evaluations, and the typical real circuit about 105 — worse, but not by a lot.

Against a properly flattened baseline, break-even depends on the workload. On the EPFL AND/INV workload each evaluation was effectively tied, so there was nothing to accumulate and 55 of 129 real circuits were marked “never.” Current B2/B4 V3 instead measured a bare CM/CSE-flat ratio of 0.8906, but its public wrapper ratio was 3.0941; any new break-even claim must therefore include preparation and the exact wrapper boundary rather than extrapolate from the bare kernel.

So the honest advice is not “use CM for repeated evaluation.” It is: work out what you are really comparing against, then work out how many times you will actually re-evaluate.

#### Technical detail

Break-even is the preparation premium divided by the per-evaluation kernel gain. A formula is classified as never breaking even exactly when that gain is not positive — preparation cost sets the magnitude of the finite counts but plays no part in the classification.

**Baselines must be matched before any two of these figures are compared.** Against plain CSE: synthetic median 78 with 35 of 192 never, prep 4.40×; EPFL median 105 with 29 of 129 never, prep 4.21×. Against CSE-flat on EPFL: median 174.5 with 55 of 129 never (43%), prep 4.11×. The synthetic-versus-plain-CSE figure and the EPFL-versus-CSE-flat figure are not a like-for-like pair and are never quoted as one.

The distributions are right-skewed with a substantial never-break-even mass in every arm, which is why the median alone is a poor summary and the histogram is shown.

Because break-even is a ratio of two small timings it moves with ordinary run-to-run variation, as does the preparation multiple. The archived run of the same synthetic corpus reports slightly different values for both; the discrepancy is recorded in section 6 under “Open discrepancies between the summary prose and the raw evidence”, and the workload-dependence conclusion is identical either way. The headline kernel ratio, by contrast, is stable across the two runs.

### My expressions have very few live variables — or quite a lot.

#### N

03

#### Verdict

The right evaluation engine changes with the workload, not at a fixed variable count

#### Verdict why

and a rule based on variable count alone gets it wrong

#### Plain-language explanation

There are several ways to actually compute the answer bits. One walks the expression recursively. One flattens it first and works over big integers. One packs bits into machine words and processes them in blocks.

The word-packed engine is the fastest of the three when there is enough work to do — but it pays a fixed setup cost on every call. On the expressions measured here that cost is not repaid until a fairly large number of variables matter, and below that the simple flattened approach wins by a wide margin.

The practical lesson is that a rule of the form “switch engines above six variables” is not safe. What matters is how much work there is to pack, which depends on the shape of the expression and not just on how many variables matter.

#### Technical detail

Flat big-integer evaluation beats the recursive kernel at every support measured, with ratios of 0.55–0.88. That part is unconditional.

The word-packed engine's fixed dispatch cost keeps flat fastest through live_k=12 on this corpus; words only wins at live_k=16, at 0.82 of flat. At live_k=6 — where a support-only rule would have switched — words is 5.8× *slower* than flat.

Restate the rule as an amortisation condition: word-packed evaluation wins when the packed work, roughly 2<sup>live_k</sup> words times the operation count, is large enough to absorb the fixed dispatch cost. Deck-era corpora with larger operation counts genuinely did cross at smaller supports. Both statements are corpus-scoped; neither is a universal threshold. A validated backend selector is listed as open work for exactly this reason.

Above live_k=16 the explicit path declines rather than producing an output that doubles in size with each further variable. Across 3,000 fresh trials the guard made 0 wrong decisions and let through 0 oversized outputs.

### I need a canonical form, an equivalence check, or a compact symbolic object.

#### N

04

#### Verdict

Use CUDD for a canonical ROBDD; use BitSet for one full vector and measure CM reuse

#### Verdict why

the required artifact and timing boundary decide the method

#### Plain-language explanation

If your real question is “are these two things the same?” or “can I keep asking questions about this rule cheaply?”, you want a standard shape. A decision diagram gives you one: build both rules the same way, testing the inputs in the same sequence, and they are the same rule exactly when the two diagrams come out identical. No need to check every case.

In the controlled B5 test, CUDD returned exact compact graphs, but its fresh-manager build was not a speed win over CM preparation. Asking CUDD to hand back the complete answer table then forces it to do the work its graph is designed to avoid: enumerate every combination, doubling the answer count with every added variable.

The practical answer is task-specific. Use CUDD when the canonical graph or symbolic operations are the deliverable. BitSet led the measured one-shot full-vector wrapper; if you are considering CM for repeated full vectors, measure its break-even against the actual baseline rather than assuming reuse makes it win. The later real feature-model audit passed saved-artifact correctness but keeps its performance rankings provisional because several timing boundaries were not matched.

#### Technical detail

Construction and evaluation are separate jobs that produce different artifacts. In B5, fixed-natural-order CUDD construction took 2.49 ms–2.58 ms including fresh-manager creation and variable declaration, yielding exact graphs of 78 nodes or fewer. Compactness is the result here; this fresh-manager timing is not a CUDD speed win over CM preparation.

When the endpoint was changed to the same complete packed vector, CUDD enumeration ran 74×–12,782× slower than the CM kernel (15.4 µs–45.4 µs), reaching 580 ms at live_k=16. The growth is structural: full extraction is linear in 2<sup>live_k</sup> assignments. This makes CM the measured winner over CUDD for that endpoint; it is not a claim that CM beats every explicit-vector method, nor that CM is a canonical symbolic replacement for CUDD.

The comparison is like-for-like: `robdd_is_cudd` held on all 192 rows and CUDD's full extraction matched the CM packed bits exactly on every one, so both sides genuinely produced the same answer.

The later real feature-model battery independently replayed the saved bounded relations without correctness mismatches, but its audit labels performance provisional: cold construction was incomplete, some warm comparisons included asymmetric first-touch work, and the historical dirty implementation state was not reconstructable. Those results do not justify a newer blanket speed ranking.

Variable ordering is a real cost centre. Trying ten seeded orders and keeping the smallest graph gave 21%–30% fewer nodes at about 8.5×–9.9× the single-build cost. CUDD's dynamic reordering never triggered at 78 nodes and below — its node ratio is exactly 1.00 — which says this corpus is small for CUDD, not that reordering is ineffective.

### My workload is real circuits, not generated formulas.

#### N

05

#### Verdict

Expect a tie against a well-built compiled baseline

#### Verdict why

the external validation is the strongest evidence here

#### Plain-language explanation

Everything above could have been an artifact of the formula generator. So the project took a published benchmark suite of real hardware circuits it had never measured against, wrote down in advance what result would count as meaningful, and ran it.

The answer: against a carelessly built competitor CM is genuinely faster — about 7%. Against a carefully built one the two came out level, with the measured difference smaller than the uncertainty in the measurement itself.

That is the honest headline. CM's case does not rest on being quicker than a well-built competitor at the computation itself, and this measurement is what settled it.

#### Technical detail

129 AND/INV combinational cones extracted from 19 circuits in the EPFL suite (20 AIG files, upstream commit 0060e15682, corpus SHA-256 bb98f14a5525). Confidence intervals are circuit-clustered, because cones from the same circuit are not independent observations.

Primary arm CM ÷ CSE-flat: 0.9998 [0.9747, 1.0249]. Secondary arm CM ÷ plain CSE: 0.9268 [0.903, 0.951].

The mechanism check is what makes “kernel-equivalent” a claim rather than a shrug. CM's advantage over a plain CSE comes from merging chains of the same operator into single wide instructions. On AND/INV circuits every gate is binary, so flattening has already captured everything there is to merge — and the instruction-count and executed-operation ratios against CSE-flat are both exactly 1.000. The mechanism predicted parity on this corpus, and parity is what was measured.

The cost side is worse on real circuits than on synthetic ones: preparation 4.11×, and 55 of 129 cones never break even against CSE-flat.

## Frontier

The 2026-08-03 campaign established parity against CSE-flat on B1/E3 and EPFL. The accepted 2026-08-25 V3 correction narrowed that conclusion: current B2/B4 measured a workload-specific bare CM advantage, while the public wrapper remained slower. Three fresh same-host repetitions ranged from 0.9049 to 0.9090, confirming the direction while exposing run-level variation that a within-run formula interval cannot measure. A later three-pod preparation confirmation passed, while a genuinely held-out i10 feature selector failed and the simple k=16 rule transferred well. The remaining questions are therefore about preparation, boundary cost, reuse, and choosing by workload rather than declaring one universal kernel ratio.

### Plain-language explanation

It is worth being clear about what kind of problem is left. “Is CM faster?” has no workload-free answer: B1/E3 and EPFL measured parity at the kernel, current B2/B4 V3 measured a modest bare CM lead, and the public wrapper remained slower. The remaining questions are about total cost, choosing, and capabilities that exist on paper but have never been shown to pay.

Three of them are cheap to answer and would move the picture immediately. Three more are the experiments that would actually test whether the structural idea is worth anything beyond re-running the same expression. Two are engineering and formal gaps. And two are honest boundary questions — regions the measurements simply do not cover.

The preparation replication and first untouched selector transfer test are complete. Synthetic cache, family, context, and tracing studies now narrow the hypotheses, and a strict workload manifest makes the missing input concrete. The next useful work starts with owner-declared real traffic; dependency-gated native comparators come only if that traffic justifies them.

### Technical detail

The B1/E3 CM-versus-CSE-flat residual remains below its pre-registered materiality bar and is not an optimisation target. ## Discipline

Each of these exists because breaking it produced a wrong published number at some point in this project's history.

### Rules

#### Item 1

##### Rule

Nothing is timed until both sides agree, bit for bit

##### Lay explanation

Before the stopwatch starts, every method being compared has to produce exactly the same answer — every bit identical. If two methods disagree, that is a bug to fix, not a data point to quietly drop. Otherwise you can measure something fast that is simply computing the wrong thing.

##### Technical explanation

Packed-equality gating across every arm and the wrapper, on every formula, before any timing is recorded. For the decision-diagram comparison this was strengthened from sampled checks to *full extraction equality* on all 192 rows, so the timed comparison is provably of the same answer produced two ways. Compile-scaling cases likewise verified packed equality across all arms on every case.

##### What goes wrong without it

A faster implementation that is subtly wrong looks like a win. Worse, an arm that fails on hard inputs and succeeds on easy ones gets timed only on the easy ones, which is survivorship bias dressed as a speedup.

#### Item 3

##### Rule

Confidence intervals are clustered on the right unit

##### Lay explanation

If you time the same expression seven times, you have not measured seven expressions — you have measured one, seven times. Treating those as seven independent facts makes your error bars look far tighter than they are. Every interval on this site is built by resampling the thing that is actually independent.

##### Technical explanation

The inferential unit is the formula, the cell, the source circuit, or the machine — never the timing round. The synthetic corpus uses a stratified-by-cell bootstrap; the external corpus uses a circuit-clustered bootstrap, because 129 cones come from only 19 circuits and cones from one circuit share structure; machines are reported individually and never pooled. Circuit clustering makes the external interval wider than a cone-level interval would be, and that width is the honest one.

##### What goes wrong without it

Pseudo-replication. Repeated rounds inflate the effective sample size, intervals shrink toward zero width, and a difference that is well within run-to-run noise acquires the appearance of statistical significance.

##### Rule

##### Lay explanation

You can time one method fully and then the other, or you can alternate between them. Those two orders leave the computer's fast temporary memory in different states, so they are genuinely two different measurements. Reporting only their average hides which one you did — so both are always shown.

#### Item 8

##### Rule

Only matched pairs are aggregated, and every refusal is recorded

##### Lay explanation

If one method manages a hard case and the other gives up, that pair cannot be averaged into a speed comparison — you would be crediting one method for the cases where its competitor was absent. Only cases where both methods answered are counted, and every case where one declined is reported separately.

##### Technical explanation

Failure-aware paired reporting: unmatched observations are excluded from ratio aggregation, and skips, guard trips and runtime refusals are counted and published rather than dropped. The external campaign reported 129 of 129 rows successful with zero runtime-guard skips; the guard sweep reports the decline rate for every cell alongside the timings.

##### What goes wrong without it

Survivorship bias. The arm that fails more often on hard inputs is measured only on easy ones and appears faster than it is.

## Glossary

### Boolean function

#### Group

boolean-basics

#### Plain-language explanation

A rule that takes a set of yes/no inputs and produces a single yes/no answer. “Is this person allowed in?” given whether they are staff, whether their pass is valid, and whether it is out of hours.

#### Technical detail

A mapping from {0,1}ⁿ to {0,1}. Everything on this site is about representing, evaluating and comparing such mappings.

### truth table

#### Group

boolean-basics

#### Plain-language explanation

A complete list: every possible combination of inputs, and the answer for each. It says nothing about how the answer is produced — only what it is.

#### Technical detail

The explicit enumeration of a Boolean function's outputs over all 2ⁿ input assignments, under a fixed variable ordering. Complete, canonical for that ordering, and exponential in size.

### variable ordering

#### Group

boolean-basics

#### Plain-language explanation

The sequence in which you consider the inputs. It makes no difference to the answer, but for some representations it makes an enormous difference to how big the representation is.

#### Technical detail

A total order on the variable set. Decision diagrams are canonical only with respect to a fixed order, and their size can vary from linear to exponential across orders for the same function.

### canonical form

#### Group

boolean-basics

#### Plain-language explanation

A standard way of writing something down such that two things that mean the same thing look identical. Once you have it, checking sameness is just checking whether the two look alike.

#### Technical detail

A representation with the property that semantically equivalent objects map to syntactically identical artifacts under fixed conventions. Reduces equivalence checking to identity comparison.

### equivalence checking

#### Group

boolean-basics

#### Plain-language explanation

Proving that two differently written rules always give the same answer — for every possible input, not just the ones you tried.

#### Technical detail

Deciding whether two Boolean functions are identical. Approaches differ fundamentally: compare complete outputs, compare canonical graphs in a shared manager, or prove the difference unsatisfiable.

### satisfiability (SAT)

#### Group

boolean-basics

#### Plain-language explanation

The question “is there any way at all to make this come out true?” Answering it does not require listing every possibility — good solvers find one answer, or prove none exists, without enumerating.

#### Technical detail

The decision problem for existence of a satisfying assignment. An existential question, distinct from the exhaustive-enumeration questions the evaluators on this site answer.

### cofactor

#### Group

boolean-basics

#### Plain-language explanation

What is left of a rule once you fix one of its inputs. Fix “is staff = yes” and you get a simpler rule about everything else.

#### Technical detail

The restriction of a function obtained by fixing one variable to a constant. The basic operation underlying decision-diagram construction and partial evaluation.

### AIG / AND-INV graph

#### Group

boolean-basics

#### Plain-language explanation

A way of writing a circuit using only two-input ANDs and inverters. Restrictive, but it makes a lot of automated reasoning simpler, so it is a common exchange format for real designs.

#### Technical detail

An And-Inverter Graph: a DAG of two-input AND nodes with optional edge complementation. The format of the external benchmark circuits used on this site.

### combinational cone

#### Group

boolean-basics

#### Plain-language explanation

One output of a circuit, together with everything feeding into it. Circuits have many outputs; a cone is the self-contained rule behind one of them.

#### Technical detail

The transitive fan-in of a single output in a combinational network. The external corpus is built from cones admitted by semantic-support bounds.

### two-level minimisation

#### Group

boolean-basics

#### Plain-language explanation

Rewriting a rule as a short list of “all of these at once” groups joined by OR — and making that list as short as possible. It is what you want if the next step is turning the rule into physical gates.

#### Technical detail

Minimisation to sum-of-products form. The AND-groups are called product terms or implicants; the dual form, OR-groups joined by AND, is the one whose groups are called clauses. Optimises expression size, not evaluation speed.

### common subexpression elimination (CSE)

#### Group

boolean-basics

#### Plain-language explanation

Noticing that the same sub-calculation appears several times and doing it only once. The workhorse optimisation behind every compiled evaluator here, and the baseline CM has to beat.

#### Technical detail

Rewriting an expression tree into a shared DAG so structurally identical subexpressions become a single node, typically by hash-consing. Evaluated once per node rather than once per occurrence.

### hash-consing

#### Group

boolean-basics

#### Plain-language explanation

Giving every distinct piece of an expression a fingerprint, and keeping only one copy of each. If you build the same piece twice, you get the same object back rather than a duplicate.

#### Technical detail

Interning structurally identical subterms via a hash table keyed on the node's constructor and children, so structural equality becomes pointer equality. The mechanism underlying both CSE and CM's canonical keys.

### sharing-aware flattening

#### Group

boolean-basics

#### Plain-language explanation

Collapsing a chain of the same operation into one wide operation — but only where doing so does not force you to redo work you were already sharing. Adding this to the baseline is what closed most of CM's apparent kernel advantage.

#### Technical detail

n-ary flattening of associative operator chains that respects the shared DAG, avoiding the duplication a naive flatten introduces at shared nodes. Its absence from an earlier baseline is the cause of a retracted headline in this project's history.

### n-ary instruction merging

#### Group

boolean-basics

#### Plain-language explanation

Turning “A and B, then and C, then and D” into a single “and all four of these”. Fewer, wider steps. This is the entire mechanism behind CM's measured kernel advantage over an unflattened baseline.

#### Technical detail

Emitting one wide instruction for an associative operator chain instead of one instruction per binary application. Predicts parity on corpora with no mergeable chains — which is exactly what the AND/INV external corpus showed.

### DAG versus tree (sharing)

#### Group

boolean-basics

#### Plain-language explanation

The same expression can be drawn as a tree, where every repeated piece is written out again, or as a graph, where repeats point back to one copy. The tree can be astronomically bigger for the same rule.

#### Technical detail

The sharing factor is unfolded occurrences divided by structural DAG nodes. Compilation cost tracking DAG nodes rather than unfolded occurrences is what makes highly shared expressions cheap to compile.

### bit-parallel / packed evaluation

#### Group

boolean-basics

#### Plain-language explanation

Instead of working out the answer for one input combination at a time, pack many combinations into a single machine word and compute them all at once with one instruction.

#### Technical detail

Evaluating a Boolean function over many assignments simultaneously by packing assignment bits into machine words and applying bitwise operations. The output remains exponential in semantic support.

### word-packed versus big-integer evaluation

#### Group

boolean-basics

#### Plain-language explanation

Two ways to hold the packed bits: as a list of machine-sized chunks, or as one arbitrarily large number. Chunks are faster once there is enough work; the big number wins when there is not, because it has less setup.

#### Technical detail

The words engine operates over arrays of fixed-width words with a fixed dispatch cost; the bigint engines operate over Python arbitrary-precision integers. Which is faster is an amortisation question, not a fixed variable-count threshold.

### BitSet

#### Group

representations

#### Plain-language explanation

The plain packed-bit executor: it computes the whole answer table using ordinary bitwise instructions and essentially no setup. It is the comparison arm CM has to beat at the whole-call boundary, and it wins at every size measured here.

#### Technical detail

The bare packed kernel used as the wrapper-boundary baseline. No structural artifact, no cache, no canonical key — and correspondingly no overhead to amortise.

### CM (Correspondence Matrix)

#### Group

representations

#### Plain-language explanation

A Boolean operator written as an ordered grid of bits, treated as an object in its own right rather than as a list of answers.

#### Technical detail

An ordered binary matrix representation of a Boolean operator. Uniqueness is relative to an ordered variable basis; matrix equality requires the same normalised ordered basis on both sides.

### LM (Logic Matrix)

#### Group

representations

#### Plain-language explanation

A second matrix form built under a different construction convention. It expresses the same things a CM does, written a different way.

#### Technical detail

A related matrix representation in the CM family, distinguished by its construction convention rather than by what it can express.

### dense CM

#### Group

representations

#### Plain-language explanation

The fully written-out matrix. Only built when the matrix itself is what you asked for — it grows exponentially with the number of variables that matter.

#### Technical detail

The materialised CM matrix, exponential in semantic support. Not the artifact produced on the packed evaluation path, and not optimised for raw execution speed.

### no-reinflate

#### Group

representations

#### Plain-language explanation

Producing the packed answer without ever building the full matrix along the way. Building it and then throwing it away would cost far more than the answer is worth.

#### Technical detail

The CM execution path that emits reduced packed output directly, skipping dense matrix materialisation when the requested artifact is a truth vector.

### IR (intermediate representation)

#### Group

representations

#### Plain-language explanation

The internal form a system compiles your expression into before running it — not what you wrote, and not the final answer, but the working form in between.

#### Technical detail

CM's structural IR is a shared DAG over interned nodes, from which an executable instruction program is lowered.

### structural hash / persistent cache

#### Group

representations

#### Plain-language explanation

A fingerprint of the compiled form, used to remember what has already been built so an identical expression can reuse it instead of being compiled again.

#### Technical detail

A digest-keyed cache of compiled structural IR, returning one object per digest. Its steady-state hit rate and size sensitivity under realistic mixes are unmeasured — one of the named open items.

### ordered CM basis

#### Group

representations

#### Plain-language explanation

The agreed sequence of variables that a matrix is written relative to. Two matrices only mean the same thing if they were written against the same sequence.

#### Technical detail

The ordered variable basis defining CM uniqueness. Basis-normalised comparison is a precondition for any matrix-equality claim.

### bra/ket measurement

#### Group

representations

#### Plain-language explanation

Reading one specific fact out of the matrix by multiplying it against a pair of pick-one-thing vectors — the equivalent of asking the operator a single question instead of unpacking all of its answers.

#### Technical detail

Logical measurement using ordered bra and ket vectors against the CM. Present in the formalism; its practical performance advantage has not been benchmarked.

### ROBDD

#### Group

representations

#### Plain-language explanation

A compressed decision tree with all duplicate branches merged. For a fixed variable order it is canonical: two functions are the same exactly when their graphs are the same.

#### Technical detail

Reduced Ordered Binary Decision Diagram. Canonical under a fixed variable order; size is order-sensitive, and extracting an explicit truth vector requires one traversal per assignment.

### CUDD

#### Group

representations

#### Plain-language explanation

The widely used library that implements decision diagrams. When this site says “CUDD”, it means measurements made with the real native library, not a re-implementation.

#### Technical detail

The Colorado University Decision Diagram package, used natively. Every measured row carries a flag confirming the native library was in use, and full-extraction equality against the packed bits was verified on every row.

### fixed-order build

#### Group

representations

#### Plain-language explanation

Building a decision diagram using one prescribed variable order, without searching for a better one.

#### Technical detail

A single build under a prescribed natural order, with no order search and no dynamic reordering. The convention used for the matched cost comparison.

### selected isolated build

#### Group

representations

#### Plain-language explanation

The build time of whichever attempt a search decided to keep. Importantly, that is not necessarily the fastest attempt — it is the one that produced the smallest graph.

#### Technical detail

The build interval of the trial retained by the configured selection objective, which prioritises node count and only then build time. Quoting it without the search total understates the true cost.

### order search total

#### Group

representations

#### Plain-language explanation

The full cost of trying several variable orders and keeping the best. It is the honest figure to quote if you searched, because you paid for every attempt, not just the winner.

#### Technical detail

The summed cost of all trial builds in a best-of-k order search. On this site it is reported beside the single-build cost and never omitted.

### dynamic reordering

#### Group

representations

#### Plain-language explanation

A decision-diagram library rearranging its own variable order automatically when the graph grows too large. On the graphs measured here it never activated, because they never got big enough to trigger it.

#### Technical detail

Automatic variable-reordering triggered by node-count growth thresholds. Node ratio was exactly 1.00 across all strata here, which characterises this corpus as small for the library rather than characterising reordering.

### nominal n

#### Group

workload-and-timing

#### Plain-language explanation

How many variables exist in the surrounding system. Not a measure of how big the job is — most of them may be irrelevant to the expression at hand.

#### Technical detail

The size of the variable namespace. Measured here to be irrelevant to cost at fixed semantic support.

### syntactically used variables

#### Group

workload-and-timing

#### Plain-language explanation

The variables that literally appear in the expression as written. Some of them may still have no effect on the answer.

#### Technical detail

Variables occurring in the expression's syntax. An upper bound on semantic support, not equal to it.

### semantic support / live_k

#### Group

workload-and-timing

#### Plain-language explanation

How many variables actually change the answer. This is the honest measure of how big a job is, and it is the horizontal axis of nearly every chart here.

#### Technical detail

The number of variables the function genuinely depends on, measured rather than assumed. Explicit output size is 2^live_k. A variable can appear syntactically and be semantically dead.

### guard skip

#### Group

workload-and-timing

#### Plain-language explanation

The system declining to produce an explicit answer table because it would be too large. A deliberate refusal, recorded as such, not a failure.

#### Technical detail

An intentional refusal above the explicit-output guard at live_k=16. Skips are counted and reported; across 3,000 fresh trials there were 0 incorrect guard decisions and 0 oversized outputs.

### wrapper

#### Group

workload-and-timing

#### Plain-language explanation

The whole end-to-end call: everything from handing over your inputs to getting the answer back, including all the bookkeeping in between — not just the computation itself.

#### Technical detail

The full call path including argument binding, environment setup, cache lookup, kernel execution and result extraction. Distinguished throughout from the kernel.

### kernel

#### Group

workload-and-timing

#### Plain-language explanation

The computation proper, with the setup and teardown stripped away. Two systems can have identical kernels and very different end-to-end costs.

#### Technical detail

The steady-state execution of the compiled program with environment and program prebuilt. At this boundary CM/CSE-flat measured parity on B1/E3 and EPFL, but a workload-specific CM advantage on current B2/B4 V3.

### wrapper overhead

#### Group

workload-and-timing

#### Plain-language explanation

The difference between the end-to-end call and the computation proper — the fixed price of using the system at all. Roughly constant, which is why it dominates when the actual work is small.

#### Technical detail

End-to-end call time minus kernel time, 50.3 µs–91.1 µs median on the current corpus and protocol. Not separable at the smallest stratum, where the fallback engine is used.

### preparation (prep) cost

#### Group

workload-and-timing

#### Plain-language explanation

The one-time cost of compiling an expression before you can evaluate it. The prep *multiple* is that cost expressed as a ratio against a named baseline — and the baseline must always be named, because it changes the number.

#### Technical detail

Compilation cost, linear in structural DAG nodes. Geometric-mean multiple against plain CSE and against CSE-flat differ and are never interchanged. It is now profiled, has one accepted memo-reduction improvement, and remains the top-ranked optimisation surface.

### prepared evaluation

#### Group

workload-and-timing

#### Plain-language explanation

Running an expression that has already been compiled and bound, so the setup is not paid again.

#### Technical detail

Execution after binding preparation is complete. Preparation is a separate one-time cost and is never folded into the per-call figure.

### break-even reuse count

#### Group

workload-and-timing

#### Plain-language explanation

How many times you must evaluate the same expression before the compilation cost is repaid. Below it you lose; above it you win. It is the single most useful number to know about your workload.

#### Technical detail

Preparation premium divided by per-evaluation kernel gain. A formula is classified never-break-even exactly when that gain is not positive — preparation cost sets the magnitude of finite counts but plays no part in the classification.

### paired observation

#### Group

workload-and-timing

#### Plain-language explanation

One timing of the same expression under two different methods, so the comparison is like-for-like. Only pairs where both methods succeeded are counted.

#### Technical detail

A matched measurement across arms for one formula. Unmatched observations are excluded from ratio aggregation to avoid survivorship bias.

### arm (baseline arm)

#### Group

workload-and-timing

#### Plain-language explanation

One of the methods being compared in an experiment. Saying “CM was 10% faster” is meaningless without saying faster than which arm.

#### Technical detail

A measurement condition in a paired comparison — here CM, plain CSE, CSE-flat, BitSet, or a decision diagram. Every ratio on this site names both arms.

### formula-level sample

#### Group

workload-and-timing

#### Plain-language explanation

The set of distinct expressions in a group. Timing one expression seven times gives you seven measurements but still only one expression.

#### Technical detail

The set of distinct formulas in a stratum — the inferential unit. An earlier pass in this project discovered that a controlled stratum contained one formula re-bound several ways, making the effective sample size one.

### ratio of medians

#### Group

workload-and-timing

#### Plain-language explanation

Take the typical time for each method, then divide. Different from taking each pair's ratio and finding the typical one — the two can disagree, so which was used is always stated.

#### Technical detail

median(A) ÷ median(B) across a stratum's observations. Distinct from the median paired ratio; both appear on this site and each is labelled.

### median paired ratio

#### Group

workload-and-timing

#### Plain-language explanation

Work out the ratio for each expression individually, then take the typical one. More robust to one expression being unusual than dividing the two typical times.

#### Technical detail

The median of per-observation A÷B ratios. Preferred where formula-to-formula variation is large.

### timing artifact / type

#### Group

workload-and-timing

#### Plain-language explanation

Exactly what a stopwatch reading includes. Setup? Extraction? Both? Every figure here says which, because comparing an inclusive figure to an exclusive one is the easiest way to publish a wrong ratio.

#### Technical detail

The labelled timing boundary: prep, kernel, end-to-end call, extraction, build. Build-window conventions that differ between runs are stated and never plotted on a shared axis.

### geometric mean

#### Group

statistics-and-protocol

#### Plain-language explanation

The right kind of average for ratios. If one measurement says “twice as fast” and another says “half as fast”, an ordinary average says 1.25 — which is wrong. The geometric mean correctly says 1.

#### Technical detail

The exponential of the mean of the logs. Used for all ratio aggregation here because ratios are multiplicative and their distribution is skewed in linear space.

### bootstrap confidence interval

#### Group

statistics-and-protocol

#### Plain-language explanation

A way of asking “how much would this number move if I had happened to test a different sample?” — by repeatedly re-drawing from the data you have and watching how far the answer wanders.

#### Technical detail

A resampling interval. The resampling unit is the crucial choice: resample the wrong unit and the interval is meaningless regardless of how many draws you take.

### clustered bootstrap

#### Group

statistics-and-protocol

#### Plain-language explanation

Re-drawing whole groups rather than individual measurements, when the measurements inside a group are related. Cones from one circuit are not independent, so whole circuits are re-drawn.

#### Technical detail

Resampling at the cluster level — circuit, cell, or machine. Produces wider and more honest intervals than naive resampling when within-cluster correlation exists.

### pseudo-replication

#### Group

statistics-and-protocol

#### Plain-language explanation

The error of counting repeated measurements of the same thing as if they were measurements of different things. It makes error bars look far tighter than they are, and can turn ordinary noise into an apparently solid finding.

#### Technical detail

Treating within-unit repeated measures as independent observations, inflating effective sample size and understating variance. The specific failure clustered intervals exist to prevent.

### degrees of freedom

#### Group

statistics-and-protocol

#### Plain-language explanation

Roughly, how much independent information your data actually contains after accounting for everything you estimated from it. Getting it wrong makes your spread estimate too small.

#### Technical detail

Residual degrees of freedom after estimating cell means. An earlier pass in this project divided a residual sum of squares by the raw observation count rather than the residual degrees of freedom, understating the spread estimate; units in singleton cells contribute no residual information.

### blocked schedule

#### Group

statistics-and-protocol

#### Plain-language explanation

Timing all of one method, then all of the other. Each method gets a run where the data it needs is likely still sitting in the computer's fast temporary memory.

#### Technical detail

All measurements of one arm, then all of the next. Reported as its own column and never pooled with the alternating order.

### round-robin schedule

#### Group

statistics-and-protocol

#### Plain-language explanation

Alternating between the methods, one after another. This keeps the two on a more even footing over time, but each one is more likely to find the computer's fast memory holding the other method's data.

#### Technical detail

Interleaved measurement across arms. Stresses cache and CPU state differently from the blocked order; agreement between the two is reported, not assumed.

### pre-registration

#### Group

statistics-and-protocol

#### Plain-language explanation

Writing down what you are going to measure and what would count as a positive result — before you have the data. It is what makes a negative result meaningful rather than merely disappointing.

#### Technical detail

Fixing corpus source, selection rules, arms, schedules, clustering basis and decision thresholds in a frozen protocol before any measurement exists.

### materiality rule

#### Group

statistics-and-protocol

#### Plain-language explanation

The pass mark, agreed in advance: how big an effect would have to be, and how confident you would have to be about it, before it is worth acting on. On the decisive experiment here, the pass mark was not met.

#### Technical detail

A conjunction of pre-registered conditions — an effect-size threshold, an interval excluding parity, and a break-even bound — all of which must hold for optimisation to be warranted. Its failure made parity the final posture for the EPFL AND/INV workload; later B2/B4 V3 prevents universalising that posture.

### packed-equality gate

#### Group

statistics-and-protocol

#### Plain-language explanation

The check that runs before any timing: every method must produce exactly the same answer bits. Fail it and the run stops rather than producing a number.

#### Technical detail

Bit-for-bit output agreement across all arms as a precondition for measurement. Strengthened to full-extraction equality rather than sampled checks for the decision-diagram comparison.

### independent reaggregation

#### Group

statistics-and-protocol

#### Plain-language explanation

Having a second, separate piece of code recompute every headline number from the individual measurements — so a bug in the summariser cannot become a published result.

#### Technical detail

Recomputation of every summary statistic from raw per-formula rows by a pass independent of the driver. Required before citation; performed again by this page's build script.

### survivorship bias

#### Group

statistics-and-protocol

#### Plain-language explanation

Judging a method only on the cases it managed to finish. If it gives up on the hard ones and its rival does not, it will look faster than it is.

#### Technical detail

Aggregation over unmatched observations, where one arm's failures are silently excluded. Prevented by failure-aware paired reporting: only matched pairs are aggregated and every refusal is counted.

### supersession

#### Group

statistics-and-protocol

#### Plain-language explanation

Formally retiring a published number — recording that it is withdrawn, why, and what replaced it — instead of quietly deleting it. Anyone who read the old version can find out exactly what changed.

#### Technical detail

A standing erratum and claim map assigning each prior claim a status of confirmed, revised or superseded with its replacement. Superseded figures appear on this site only in the corrections ledger and are never plotted.

### EPFL benchmark suite

#### Group

statistics-and-protocol

#### Plain-language explanation

A published, freely available collection of real hardware circuit designs, widely used for comparing logic tools. Using it means testing against something the project did not choose or shape.

#### Technical detail

The external combinational benchmark suite from which 129 AND/INV cones across 19 circuits were extracted, at a pinned upstream commit with per-file digests recorded.

### identity fields

#### Group

statistics-and-protocol

#### Plain-language explanation

The parts of a benchmark row that say *which* expression it is, as opposed to how fast it ran. If those match exactly between two runs, you know both runs asked the same questions.

#### Technical detail

Non-timing row fields — formula id, truth digest, support, structural counts. Exact match across runs establishes that a difference is timing, not workload.

### sanity gate

#### Group

statistics-and-protocol

#### Plain-language explanation

A cheap check that runs before the expensive work and stops everything if it fails — such as a small pilot run, or verifying the test set's fingerprint.

#### Technical detail

A deterministic pilot plus a pre-registered runtime bound before each full run, alongside corpus digest verification and truth-digest re-verification at measurement time.

### Purpose

Audited, field-specific benchmark candidates for testing whether a reusable CM structural artifact creates value beyond a one-off Boolean answer.

### Interpretation rule

A result on a CM-shaped synthetic stress suite is a mechanism demonstration, not domain dominance. A domain claim requires a preregistered confirmatory result on the natural corpus with the best artifact-equivalent incumbent.

### Fairness protocol

Freeze dataset revisions, parsers, translations, exclusions, seeds, and resource limits before timing.

Run every eligible natural-corpus item; do not retain only formulas on which CM is fast.

Separate cold construction, warm evaluation, version update, partial-context update, serialization, and explanation or change-impact tasks.

Compare equivalent outputs and capabilities. SAT witness search, BDD graph construction, explicit truth-vector generation, and policy authorization are different artifacts.

Publish failures, refusals, timeouts, memory peaks, and never-break-even cases alongside successful timings.

Label synthetic stress results separately and sweep the property intended to help CM: reuse, edit locality, shared-subgraph fraction, context delta, and residual semantic support.
