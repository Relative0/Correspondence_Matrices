# Task diagnostic methods

## Scope and execution

`task_diagnostics.py` is audit-local. It loads the historical Y02–Y05 helper by exact SHA-256 (`47ca5daf1d402e7c2c7e30140727699f0a67eb996f30d3688f219e803a666bd5`) from the dirty root as a named historical adapter. The baseline `cm_ir`, `bitset_backend`, `cm_exprlib` and `cm_bench` import paths are checked against the exact-commit worktree. The root helper does not replace baseline production code. It supplies parsing, independent scalar oracle, deterministic assignment generation, packing and the unchanged `_cm_batch_values` evaluator interface.

The exposed input file SHA-256 is `d40e8863a8a004a6dee6fd7cc6f014055c38465d74db6a38dda4e1c9307b0dad`. Cases used are absorption-k4, contradiction-k4 and balanced-k8. Family sources are the disclosed unit-test seeds 2 and 3 and the plan's declared identical/mutation treatments. No held-out fixture was loaded. All output sizes are small (largest emitted expression 996 bytes; assignment output 512 bytes). The original root and consolidation worktree are never mutated.

`task-run-001` completed 70 cells across 18 matched groups in **44.120 seconds**. Each group is one fresh child process, bounded at 60 seconds. It imports common runtimes once; independent scalar references are prepared before timing. Five uninstrumented repeats rotate and reverse arm order, with cache clear and freshly parsed/generated input per sample. All uninstrumented samples in a matched group finish before its three separate phase passes, one cProfile pass and one tracemalloc pass per arm. There is no cross-arm parallel timing. The suite deadline is 30 minutes; no retry or widening was needed.

Runtime/import timing is recorded once per matched group and duplicated only as an annotation on its arms. The enclosing subprocess wall time includes **all** matched arms and their timing/profile/memory/structure passes; it is not a one-call latency, and it must not be summed across arms. A fresh library session is measured after imports, while q64 means compile once and serve 64 contexts inside one session. Ordinary import caches, SymPy process caches and OS file caches are not reset. These are resident-import, cold packed-cache sessions, not fully cold operating-system measurements.

The runner source hash during `task-run-001` was `57e95c85b3f54dfaf7d7943057f1c87282b86855f2b014cb8824133797cc4504`. The script remains unchanged after the run. Derived summaries are recomputed with `analyze_task_diagnostics.py`; immutable raw timing files are not rewritten.

## Exact attribution boundaries

- **Supplied assignment batch:** all three raw/CSE/CM adapters call the same historical NumPy evaluator. `BatchNode` is an audit-only interface object; raw preparation preserves existing identity sharing, and CSE preparation interns structurally identical ordered subexpressions. It has no CM support metadata, public recursive keys or semantic rewrites. CM compilation can rewrite and flatten. All 4096 answers are checked exactly and packed identically. This is a controlled ingress comparison through a common eligible evaluator, not a proposed product backend.
- **Input scope:** `supplied_assignment_loading` is the **construction of deterministic assignment rows**, not I/O reading an already supplied batch. It is intentionally charged equally, matching the disclosed worker protocol. `input_document_loading_json_decode` reads and decodes the small exposed JSON document. Both can dominate these tiny kernels. Report their exclusive spans separately when reasoning about a caller that already holds decoded input.
- **Assignment kernel scope:** the unchanged historical `_cm_batch_values` combines assignment-array construction, recursion/memoization, NumPy operation dispatch, temporary allocation, and NumPy-to-Python-list conversion. The grouped phase is named `assignment_binding_kernel_array_to_list`. It cannot be split into unbiased kernel, allocation or output-list percentages from this pass. SymPy has different conversion boundaries and uses a different compiled evaluator; its comparison is algorithm/preparation comparison.
- **Restriction:** both arms lower into baseline `FlatProgram`, bind with the same `_bind_flat_program`, and execute the same `PreparedFlatEvaluation`. CSE uses `flatten=True`; CM uses normal share-aware IR compilation. Both preserve ordered basis and fixed assignments. The q64 treatment cycles the four contexts fixing x0 and x1; it delivers all 64 six-variable cofactors. This measures repeated-context reuse, not 64 independent arbitrary restrictions. The prepared executor uses no dead-slot releases at this small width, matching the production release threshold.
- **Count/SAT/equivalence:** CSE and CM use identical packed primitives and derive count with `bit_count`, SAT with a nonzero-bit test, and equivalence with full-bit equality. SAT witness is validated by a scalar evaluation. This isolates ingress into the same explicit evaluator. SymPy SAT uses `dpll2`; exact-count comparison uses exhaustive `truth_table` consumption, **not an advanced symbolic model counter**. Solver/ROBDD/counting conclusions beyond these controls require the task-matched frozen evidence.
- **Expression delivery:** CSE and CM feed minterms to the same `SOPform`. Both serialize a complete DNF expression and exhaustively verify its semantics, with expression-quality inspection. SymPy default/forced arms use `simplify_logic`. The common-minimizer pair isolates ingress, while `simplify_logic` comparison changes algorithms. Exact verification stays in an explicitly charged phase.
- **Family core:** the CSE/core-CM arms deliver packed truth bytes for every variant through the identical prepared executor. Cache-enabled compilation reuses actual CM persistent nodes/programs; mask cache is cleared once per session. Reference generation is explicitly charged. Compiler detailed diagnostics are disabled for uninstrumented custom core-family samples; cache counts come from separate phase passes.
- **Public family:** the actual `_cm_family_workload` is called unchanged and retains its internal IR timers and validation, because those are part of its existing implementation. Surrounding phases reconstruct reference creation and family structural diagnostics from `time_expression_family_workload`, plus disclosed-fixture generation. This is an audit-local reconstruction of those outer preparation stages, **not** a timer around the complete multi-backend `time_expression_family_workload` function. Its output contract is family statistics with internally verified relations; the core-family contract explicitly delivers packed relations. Do not subtract the two whole-call times and call the difference pure wrapper overhead. Nested legacy compile/eval/total spans support attribution inside the public-family arm.

## Data interpretation

`TASK_SUMMARY.json` contains all 70 medians and exclusive phase means. Each wall share equals the mean of phase wall times divided by mean caller wall time from the **same phase pass**. This weighted aggregation sums to 100%, unlike a sum of independent phase medians. CPU shares use the corresponding phase CPU mean denominator. cProfile self/cumulative call counts and mean self cost remain in the raw cell records, referenced by JSON pointer-like paths; cumulative columns must not be summed. All cProfile and tracemalloc timings are separate from uninstrumented samples.

Windows process CPU increments observed here include 15,625,000 ns. Most submillisecond cells therefore record zero CPU time, and even a short process-CPU span can jump one tick. A recorded zero means unresolved below timer resolution, not zero computation. Phase CPU percentages are often null or quantized and do not establish CPU attribution at helper scale.

Tracemalloc reports current/peak/net Python-traced bytes, including remaining caches and returned diagnostic metadata. It does not measure cumulative allocations, all NumPy/native memory, or resident process memory. Absolute native-RSS and cumulative-allocation fields stay null. Tracing peaks cannot be added to retained sizes or compared to uninstrumented latency as if tracing were free.

Two custom-family fields in raw `task-run-001` require an explicit analysis correction: uninstrumented `cache_counts.hits/misses` are zero placeholders because `diagnostics=None`. They are **not measured zeros**. `TASK_SUMMARY.json` sets uninstrumented hit/miss values to null and presents actual counts only from separate phase passes; public-family legacy counters are valid in all passes. The source records are preserved. No timing conclusion relies on those placeholders.

`family_cache_context` is an additional untimed reconstruction: it records shared associative classes, root-only versus subtree cache mode, and whether each root existed before compilation. It is separate from the timed samples. This distinguishes root reuse from many cheap leaf/subtree hits and verifies whether negligible reuse was actually realized.

No optional dependency was installed. SymPy was already available. No SAT, BDD, cloud, default routing or product behavior changed. All new timings are diagnostic observations, not confirmation benchmarks or a new scientific disposition.
