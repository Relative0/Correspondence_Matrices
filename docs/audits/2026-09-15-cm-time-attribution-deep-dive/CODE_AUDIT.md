# Read-only implementation audit

Base: `e334de594262059cc18cf37eaab56b0f79e94843`. Source references below are repository-relative paths and one-based line numbers at that commit. All conclusions in this document are **code-supported inference** unless explicitly labelled otherwise. No profiler output or new timing is used here. Comments describing earlier measurements are not treated as measurements from this study.

## 1. What CM IR actually retains

`CMNode` (`cm_ir.py:477`) stores kind, a nested structural key, a sorted variable tuple, constant information, operation, child references and variable name. It does **not** store a complete truth table at every node. Explicit intermediate arrays appear when a materializer is invoked (`cm_ir.py:1475`), or packed bitsets during packed execution (`bitset_backend.py:120`). Therefore “full information” has two distinct meanings: symbolic structural information retained in the IR, and enumeration of a requested complete relation. Only the latter necessarily has an exponential number of output bits.

`node.vars` is the support retained after the implemented local rewrites, not a proof of the minimum semantic support of an arbitrary function. `_live_vars_union` unions child variable tuples and sorts them (`cm_ir.py:723`). A downstream restriction removes fixed variable names. The no-reinflate wrapper uses this resulting width for the packed/fallback decision, but the actual packed width is the requested output-variable count unless reduced output was explicitly allowed (`cm_ir.py:2113`, `cm_ir.py:2144`, `cm_ir.py:2159`). A function with few retained live variables can still require a complete, much larger output if that is the caller's contract.

The node's public `key` is nested tuple structure pointing at child keys; it is not a textual tree expansion. Actual retained bytes must be measured with object-identity deduplication. Deep hashing, comparisons and sorting can nevertheless walk nested structure. `CMNode.__hash__` lazily caches its field-wise hash (`cm_ir.py:487`), while dataclass equality remains structural. The NumPy materialization memo uses `(CMNode, fixed-subset tuple, allow-collapse)` keys (`cm_ir.py:1486`, `cm_ir.py:1609`); packed CM recursion uses object IDs instead (`bitset_backend.py:141`). It would be incorrect to attribute deep CMNode hashing to the packed recursive evaluator.

## 2. Building and canonicalization

The default `compile_expr_to_cm_ir` enters `compile_expr_to_cm_ir_cached` (`cm_ir.py:1204`, `cm_ir.py:1238`) with reuse disabled unless requested. The default builder first performs an iterative structural UID/fanout pass (`cm_ir.py:1052`, `cm_ir.py:1140`), then recursively constructs the canonical graph with a structural UID memo (`cm_ir.py:1154`). The memo prevents rebuilding a structurally equivalent class even when separate source objects represent it. The source prepass merges commutative operand order for AND/OR/XOR/EQV while preserving implication order.

Canonicalization splices same-operation associative children except a shared subchain protected by `no_splice`, and sorts operands by deep `node.key` (`cm_ir.py:740`). AND/OR rewrite loops use compact builder-local UIDs for duplicate and complement checks (`cm_ir.py:775`, `cm_ir.py:836`). XOR counts UID parity and sorts remaining nodes by key (`cm_ir.py:895`). EQV and implication use structural equality/complement/constant rules (`cm_ir.py:947`, `cm_ir.py:1007`). These rules can eliminate executed work; comparing different final program lengths is a representation-plus-rewrite comparison, not an isolated dispatcher comparison.

Interning constructs compact keys from operation and child UIDs, looks up a Python dict, and creates a dataclass on misses (`cm_ir.py:635`). It does not hash the public deep key at that lookup. Support propagation, deep public-key construction and interning remain separate work. Persistent-cache subtree hits may introduce nodes from other builders. `_node_uid` then calls `_adopt_foreign`, which walks the foreign graph, interns structural twins and keeps foreign nodes alive for the builder lifetime (`cm_ir.py:575`, `cm_ir.py:586`). This is a concrete reuse-management cost that a hit counter alone does not reveal.

The raw expression `expr_vars` helper is a recursive tree-occurrence traversal (`cm_ir.py:459`, `cm_ir.py:2292`), unlike the UID pass. Calling it repeatedly on a heavily shared source DAG can walk repeated occurrences; the assigned local measurements must verify whether a measured caller actually invokes it before attributing that mechanism.

## 3. Compile cache semantics and what can amortize

| Cache | Lifetime/key | Retained work | Recurring work / limits |
|---|---|---|---|
| Ordinary IR cache | Process; `(expr, share_aware_flatten)`; `cm_ir.py:78`, `cm_ir.py:1247` | Root CMNode graph | Opt-in; structural Expr hash/equality lookup; LRU update; max 4096 entries. The code is not an identity-keyed cache despite a docstring referring to identical immutable objects. |
| Persistent IR cache | Process; association-preserving, commutative-canonical BLAKE2b-128 digest plus flatten flag; `cm_ir.py:235`, `cm_ir.py:285` | Root or subtree CMNode graphs | Sharing-class prepass and digest work on each call, lookup/LRU update, max 16384 entries. | Builder interning | One builder | Canonical nodes, compact UID registry, adopted foreign keepalive | Fresh builder work unless caller actually retains builder; no persistent execution output cache. |
| Root-attached flat programs | CMNode or Expr object; `bitset_backend.py:361`, `bitset_backend.py:585`, `bitset_backend.py:697` | Instructions, loads, release schedule, bound caches, optional word plan/scratch | Fresh root means lowering recurs. Separate raw/CSE/CSE-flat attributes avoid flag aliasing. |
| Bigint mask environment | Process LRU by complete ordered variable-name tuple; `bitset_backend.py:16` | Immutable variable bit columns | Max 256 entries; a new tuple/order/width can require masks again. Cold cost includes output-width-sized byte/int construction. |
| Bound input template | FlatProgram FIFO by `(vars_key, fixed_present, fixed_values)`; `bitset_backend.py:374` | Slots holding input masks and full mask only | Scans load variables to encode fixed values each call; max 64 bindings. Operation outputs are never cached. |
| Word environment/constants | Process LRU; `bitset_backend.py:817`, `bitset_backend.py:830` | Read-only arrays constructed from bigint masks/constant bytes | Max 4 environments and 8 constants; word environment depends on bigint environment too. |
| Word plan/scratch | Plan per program; scratch per program/thread/word width; `bitset_backend.py:873` | Scratch arrays for planned live operation results | Max 2 scratch widths per program/thread, FIFO. Input resolution and all operations recur. Output conversion recurs. |
| Alignment plans | Process LRU by source and target variable tuples; `cm_ir.py:1344` | Transpose axes and inserted-axis positions | Max 4096; applying views and final materialization recur. |
| Root node count/hash | Root/node-attached lazy fields; `cm_ir.py:487`, `cm_ir.py:1832` | Integer hash or node count | First use traverses relevant structure; later calls reuse it. |
| Recursive evaluator memo | One evaluation call | Intermediate integers or tagged arrays | Recreated on every call; retains visited results through the call. |

Persistent caching has two regimes (`cm_ir.py:344`): any shared associative class selects **root-only caching**, because sharing-aware shape depends on context; no such class permits subtree caching. A tiny mutation to a root in the first regime can therefore miss even when almost all source structure is shared. Persistent compilation also executes its sharing prepass once before deciding the regime, and `builder.build` executes another prepass on a root miss (`cm_ir.py:346`, `cm_ir.py:353`, `cm_ir.py:1141`). A root hit avoids build/lowering only if the cached root already carries the flat program. `reuse_cache` is accepted by the persistent API but does not disable the persistent cache; dispatch is controlled by `persistent_cache`.

The exact probability argument in the digest docstring is not an observed collision experiment. The implemented fact is absence of a structural equality fallback. Cache hit counts quantify entries, not saved work, and cannot alone establish an amortization break-even.

## 4. Raw AST, CSE-flat and CM-flat are different controls

`eval_expr_bitset` is already identity-memoized (`bitset_backend.py:65`). It cannot be labelled the no-memo raw-recursion arm. `_eval_expr_bitset_fixed` is an existing no-memo recursive helper with fixed-variable support (`cmbench/expr/partial_contexts.py:126`). The ordinary raw engine requires that helper for restricted contexts (`cmbench/backends/bitset_engine.py:43`). A diagnostic no-memo arm must explicitly state its entry point.

`compile_expr_flat` emits every subtree occurrence (`bitset_backend.py:546`), including repeated DAG subchains. The raw engine selector's flat and words choices still route through this no-CSE lowering (`cmbench/backends/bitset_engine.py:84`). Comments about a “production baseline” in `compile_expr_cse` do not change that routing. The strongest structural control must explicitly call `get_expr_cse_program(..., flatten=True)` or its evaluator.

`compile_expr_cse` iteratively interns compact `(opcode, child UID...)` keys without CM rewrites, support tuples, deep CMNode keys or commutative sorting (`bitset_backend.py:599`). Its optional associative flattening splices only single-consumer children. Thus it preserves structural sharing while retaining a smaller *kind* of execution representation. Whether the representation is smaller in bytes and whether that explains a measured win require retained-object and timing data; neither follows from instruction counts alone. Long flattenable chains also build successive flattened argument tuples (`bitset_backend.py:665`), so the compiler's linearity comment must not be generalized to every `flatten=True` chain shape without scaling measurements.

`compile_flat(CMNode)` walks the already canonical CM DAG once by object ID (`bitset_backend.py:329`). CSE and CM can execute literally the same `PreparedFlatEvaluation` / `_eval_prepared_flat` loop after binding (`bitset_backend.py:408`, `bitset_backend.py:423`). This is the clean local mechanism control. The normal public `eval_cm_node_flat` has a near-identical inlined loop and includes attached-program lookup plus binding (`bitset_backend.py:493`). The raw no-CSE flat loop uses binary operations directly (`bitset_backend.py:758`); it is not exactly the same loop as the n-ary prepared executor.

Flat instruction count is not executed primitive count. `program_metrics` (`bitset_backend.py:274`) defines both bigint and words primitive counts, operand edges and planned peak live word buffers. For example, n-ary AND/OR/XOR performs arity minus one combines, and implication/equivalence require multiple primitives. Its word-plan calculation is observationally pure: it does not warm `prog.word_plan` when absent (`bitset_backend.py:313`). Collecting other metrics that call a cached accessor can still warm state and must be separated from cold timings.

## 5. Memory, liveness and output conversion

Bigint recursive memos retain every computed result until return. Flat bigint evaluation copies the input slot template on each call; operation integers are allocated by Python/C bigint operations. References to dead slots are cleared only when both live width is at least 18 and slot count at least 64, unless explicitly disabled (`bitset_backend.py:211`, `bitset_backend.py:510`). Under smaller conditions, all operation results remain reachable from the values list until return. Allocation and release are inside the kernel; they are not independently timed phases in existing code.

Word evaluation uses a last-use schedule to color operation results onto scratch buffers, allocated per program/thread/width and reused (`bitset_backend.py:836`, `bitset_backend.py:873`). An output buffer cannot alias its inputs; a dying input buffer becomes available only after its consumer. This deliberately differs from bigint retention. NumPy `out=` avoids allocating a new result array for each operation in steady state; it does **not** make the entire public call allocation-free: `resolve` work and Python objects remain, and `root_array.tobytes()` plus `int.from_bytes` creates returned data every time (`bitset_backend.py:941`). Calling all of `_eval_words` “kernel time” would conceal plan, environment, scratch and output conversion work.

`bitset_to_bool_array` converts a packed integer into bytes and unpacks to one uint8 element per assignment (`bitset_backend.py:106`). The hypercube helper then converts dtype to bool and reshapes (`bitset_backend.py:115`). This is output conversion, not logical evaluation. A packed complete relation has at least one bit per assignment; a dense bool/uint8 relation consumes a byte per assignment in these APIs. Dense CM materialization also aligns, broadcasts and forces a final `.copy()` (`cm_ir.py:1968`). Requested complete output still grows exponentially even when the simplified function is constant.

The hybrid/NumPy materializer uses support-specific arrays and alignment, may collapse small subgraphs to bitsets then expand those bitsets back to arrays, and performs its own local constant propagation (`cm_ir.py:1507`, `cm_ir.py:1608`, `cm_ir.py:1680`). `pieces` evaluates all children before AND/OR's constant checks; a later dominating constant does not retroactively avoid those child evaluations. Array alignment often creates views; final output copy is the materializing operation. Actual peak memory, retained memory and all allocations cannot be inferred solely from `.nbytes` of the returned array.

## 6. Public wrapper and family lifecycle

`materialize_hybrid_no_reinflate` validates threshold/output budget, obtains root node count (cached after first call), determines live and output variables, selects engine, executes, and constructs `FinalNoReinflateResult` (`cm_ir.py:2006`). It is an evaluator for an existing node: it does **not** include source-to-IR compilation. `compile_expr` includes an additional associative structural digest before compiling (`cm_ir.py:1292`); `evaluate_compiled` delegates to no-reinflate materialization (`cm_ir.py:1310`). `compile_expr_to_cm` combines compilation with dense output materialization (`cm_build.py:26`). Any report using “public CM” must identify which boundary it means.

Diagnostics materially change the no-reinflate public path. A diagnostics-free flat/words call can take the fast branch (`cm_ir.py:2033`); providing even an empty diagnostics dict prevents it and uses the generic branch (`cm_ir.py:2092`). Consequently phase timings from the generic diagnostic path are not additive components of an independently timed fast path. Profile them as different treatments, or use a non-invasive sampling/cProfile pass and retain unknown residual.

`_cm_family_workload` always clears the persistent cache before the family (`cm_bench.py:928`), then creates a timing-enabled diagnostics dict per variant, compiles, executes public no-reinflate CM, converts output for a reference comparison and collects counters. It does not pass `flat_eval=config.cm_flat_eval` directly to the wrapper (`cm_bench.py:946`); that selection relies on the module default managed by the caller, whereas words is explicit. Direct family invocation must scope both evaluation defaults to hold evaluator selection constant.

Per-variant times end before output conversion/correctness checks; family total includes those checks and list/accounting work (`cm_bench.py:961`, `cm_bench.py:968`, `cm_bench.py:979`). Reference construction occurs before all backend totals in `time_expression_family_workload` (`cm_bench.py:1061`), and recursive direct-BitSet environment construction is also outside its total (`cm_bench.py:1093`, `cm_bench.py:1097`). These are timing contracts, not free computation. The family wrapper return itself and result serialization occur after the recorded total. Disabled persistent caching removes one reuse mechanism but does not disable input-mask, root-attached program or alignment caches.

The ROBDD family shared-manager number only times adding expressions after manager creation/declaration/order choice (`cm_bench.py:1016`, `cm_bench.py:1021`) and does not extract a complete packed relation. The separate ROBDD family path explicitly sets `measure_tt_extract=False` (`cm_bench.py:1174`). These numbers are representation-construction comparisons, not same-output CM attribution.

All these existing clocks use `perf_counter`; none of the assigned three modules records process CPU time per phase. Counter means (`time/count`) are interpretable only when their call counters and timers have the same gate and scope. Many counters are conditional on `ir_timing_enabled`; zero may mean disabled measurement. Frozen records can recompute ratios, disjoint residuals and percentages where denominators share boundaries, plus structural derived quantities already present. They cannot retroactively recover process startup, parsing, CPU split, allocation count, cache lookup/validation duration, or exclusive helper time.

## 8. Classification boundaries

* **Inherent explicit-relation/output cost:** emitting all requested relation bits; dense API byte expansion is an explicit representation contract. Complete-relation costs apply equally to task-matched direct BitSet.
* **Task/algorithm mismatch:** comparing complete relations against SAT/count/equivalence status, assignment-only answers, or BDD construction without extraction. A packed relation can answer these queries, but computing all rows is not implied by a smaller requested answer.
* **CM representation cost:** canonical CMNode creation, retained support and deep structural keys, support propagation and CM-to-flat lowering where source-to-CSE can directly produce a program.
* **CM-family reuse-management cost:** recurring digests/UID prepass, root-only versus subtree regime, lookup/LRU/foreign adoption, repeated diagnostics/accounting.
* **Current implementation/runtime cost:** Python traversal, dict/list/dataclass/tuple work, deep comparison, bigint allocation/retention, dispatch, input lookup and scratch management. These mechanisms are not mathematical requirements of CM.
* **Wrapper/lifecycle cost:** default selection/import, budget guards, node-count cache miss, result wrapping, family reference/check/aggregation and any external process/worker lifecycle.
* **Output conversion/delivery cost:** bytes/int/array transformation, final copies, serialization and transfer where included by a caller.
* **Comparator-specific preparation:** CSE structural interning, BitSet masks, ROBDD order/manager/build, SAT encoding and solver initialization, symbolic import/translation; must be charged consistently.
* **Unresolved:** exclusive phase shares absent from records; interactions of rewrites, program size, cache hits and object retention; process/native allocator attribution; cross-machine cause without matched phase evidence.

No performance disposition, routing choice or implementation default is changed by this audit.
