Part one · For everyone

What is actually being compared?

Both methods answer the same kind of question: given a logical formula — a statement built from variables and connectives like AND, OR, NOT ("if A and not B, then C…") — work out its answer for every possible combination of true/false inputs. With n variables there are 2n combinations: about a million at n=20, almost 17 million at n=24. The full list of answers is called a truth table.

Bitset — the direct method

Takes the formula exactly as written and evaluates it for all combinations at once, using a clever packing trick: all 2n answers ride inside a few very wide binary numbers, so one machine operation advances millions of rows together.

Its character: simple, direct, brutally effective. It does exactly what you wrote, no more, no less.

CM — the "understand first" method

Before computing anything, it rewrites the formula into a tidy standard form: folding away constants, cancelling contradictions, merging every repeated sub-formula into a single shared piece, and discovering which variables don't actually matter. Only then does it compute — using the same packing trick on the simplified formula.

Its character: it reads the formula before running it.

Nothing is approximated — the answers are identical

A fair worry about any "simplify first" approach: does simplifying lose something? Here, provably not. CM's rewrites are all exact logical identities (like "x AND x is just x"), so the simplified formula gives the same answer as the original for every single input. This isn't taken on faith: the audit compared CM's output against a slow, independent brute-force calculation over 134 million truth-table rows with zero mismatches, on both Python versions installed on this machine. What CM gives up is only the original phrasing of your formula — the way it was parenthesized and ordered — never its meaning.

What the charts show, in words

  • The engine room (kernel, blue & teal bars): stripped to pure computation, CM is the faster machine — typically 5–20% quicker, sometimes more. Its edge comes from the merging step: if the same sub-formula appears five times, Bitset computes it five times, CM computes it once.
  • The front desk (wrapper, yellow bars): the complete CM function also checks safety limits, works out which variables matter, and packages the result. That overhead is tiny and fixed — a few millionths of a second — but the computations in this chart are themselves only a few millionths of a second, so it nearly doubles the bill and CM falls 14–26% behind. On big computations the same overhead is around half a percent: irrelevant.
  • The tipping point: the more a formula collapses under simplification, the less work CM has left — while Bitset still executes every operation of the original formula. In the 300-formula campaign, formulas that kept only ≤4 relevant variables tipped end-to-end CM ahead of the Bitset (ratios 0.87–1.0 at the larger sizes), front desk and all; formulas that stayed complex left Bitset modestly ahead.
  • A lesson in sample size (and honesty): an early 8-formula pass showed CM winning outright at n=24 (0.84). Rerunning with 300 formulas per size showed that was luck — the true n=24 figure is 1.02, a statistical tie. The big campaign also caught a mis-tuned internal setting that had been making ~20% of formulas ~40× slower on the CM side; with it fixed, no pathological cases remain. Bigger samples made the result both fairer to Bitset and kinder to CM's worst case.
  • The frontier (chart 3): when formulas are built so that every variable genuinely matters, CM computes the complete answer 1.4–3.3× faster all the way to n=32 — 4.3 billion rows in 3.9 seconds versus Bitset's 7.8 — though that family plays to CM's strength (repeated sub-formulas). And the formulas the safety guard normally refuses turn out to be perfectly computable: computed exactly over the variables that matter, they land in a dead heat (≈0.96). The refusal was always a size policy, never an inability.

So where is CM's real value?

Not in shaving microseconds. The honest speed verdict is "roughly a tie". CM's value shows up when problems get big:

  • It can answer questions the direct method must refuse. A 24-variable truth table has ~17 million entries; at 30+ variables, storing one becomes absurd. But if only 6 of those variables actually matter, CM detects this and returns the exact 64-entry answer instead — with a certificate of which variables were irrelevant. The direct method, taking the formula at face value, has no way to know this in advance.
  • Its answers are compressed but exact — a small table plus the list of variables it depends on, rather than an astronomically large one padded with repetition.
  • It behaves like a compiler. The tidy standard form is built once and reused: evaluate the same formula under different fixed inputs and the expensive preparation is already done. Identical formulas — however differently written — are literally recognized as the same object.

Part two · For experts

The pipeline, precisely

Four stages, with an explicit statement of what each preserves:

  1. Source AST. The propositional expression as written (Var/Not/And/Or/Xor/Imp/Eqv tree). Kept alongside; nothing below mutates it.
  2. Canonicalizing construction → interned CM IR. Bottom-up rewriting into a canonical DAG (cm_ir.py constructors). Function-preserving, syntax-discarding: the Boolean function is exactly preserved (every rewrite is a logical identity); the original parenthesization, argument order, duplicate subterms, and eliminated branches are not recoverable from the IR. The result is still a structural formula (an operator DAG over named variables with a computed live-variable set node.vars) — not a truth table.
  3. C1a flat compilation (compile_flat). Fully lossless. The interned DAG is topologically linearized into a slot program — one instruction per unique DAG node. No rewriting occurs here; it is purely an execution format (no recursion, no memo lookups, compile-once cacheable). Verified bit-identical to the recursive evaluator across the full audit sweep. This is what "the C1a flat compiler reversed the kernel gap" means: same canonical formula, better engine.
  4. Arithmetic engine. Packed-bitset evaluation over Python bigints, or (since this audit) numpy uint64 word vectors — both available to CM and to the Bitset baseline, so engine choice never tilts the comparison.

The canonicalization rule set (from the code)

  • Flatten + sort: associative ops are flattened to n-ary and arguments sorted by canonical key — commutativity and associativity are normalized away, so (a∧b)∧c ≡ c∧(b∧a) intern to one node.
  • Constant folding: x∧0→0, x∧1→x, x∨1→1, x∨0→x; IMP/EQV fold constants analogously.
  • Idempotence: duplicate arguments deduped (x∧x→x).
  • Complement annihilation: x∧¬x→0, x∨¬x→1, detected pairwise against the flattened argument list.
  • XOR arithmetic: argument multiplicities taken mod 2 (pairs cancel entirely), constants folded into a parity bit, trailing parity emitted as a negation (x⊕1→¬x). The most aggressive rule — it is why (a⊕b)≡(a⊕b) collapses to a constant with zero live variables.
  • Double-negation elimination via the negate() constructor.
  • Hash-consing: every structurally identical subformula anywhere in the expression becomes one shared, interned node. This is simultaneously the compression mechanism, the kernel speed edge, and the cache key.

Why CM computes fast — three separable mechanisms

  1. Work scales with 2live_k, not 2n. Canonicalization computes the true support of the function. A 24-variable formula with 6 live variables costs a 64-bit-wide evaluation, not a 16.8M-bit one, and the output guard (live_k ≤ 16) makes infeasible requests an explicit, checkable refusal rather than an OOM. Note this is a capability, deliberately neutralized in the speed benchmarks: the fair Bitset control is granted the same reduced scope, so matched-scope ratios never credit CM for it.
  2. DAG sharing: one instruction per unique subformula. The flat program's instruction count is the number of unique nodes; the Bitset baseline executes every occurrence in the original AST. This is the entire source of the ~0.6–1.0 kernel ratios — real, but modest on random formulas.
  3. Compile-once caching. Interning makes programs and bound input-mask templates safely cacheable across evaluations and across different fixed-variable bindings.

The wrapper economics

The public entry point (materialize_hybrid_no_reinflate) adds guard checks, live-variable scope planning, and result-object construction: a roughly fixed 3–5 µs per call. Against a 2–6 µs kernel (chart 2's reduced-scope regime) that is a 1.02–1.25× end-to-end deficit at the medians (300 formulas/n); against an 84 ms full-output computation at n=22 it measured ~0.5%. The audit also landed a diagnostics-off fast path that trims this, verified path-equivalent to the instrumented reference.

The 300-formula campaign: sampling, stratification, and a threshold fix

An early 8-formula-per-n pass showed the wrapper ratio at 0.84 at n=24 — CM winning. Suspicious of the sample size, we reran with 300 formulas per n (1,500 total, 5 interleaved timing rounds each, every trial verified bit-correct). Findings:

  • live_k is n-independent, as theory predicts: a depth-4 tree has ≤16 leaves drawing uniformly from n variables, minus canonicalization's eliminations. Measured: median live_k 5–6, p90 8–9, max 11–12 at every n from 16 to 24. The early n=24 batch drawing all eight ≤6 was a few-percent-probability accident; the robust n=24 median ratio is 1.02, and the corrected chart shows it.
  • Stratified by live_k (threshold-16 configuration): live_k ≤ 4 → CM ahead or tied end-to-end (0.87–1.06 across sizes); live_k 5–7 → Bitset modestly ahead (1.05–1.28); live_k ≥ 8 → Bitset ahead (1.12–1.38).
  • The threshold discovery: under the published hybrid_threshold=7, every live_k ≥ 8 formula (~20% of draws) was routed to the numpy TT-vector fallback and ran ~40× slower than the Bitset — a mis-tuning the 8-trial medians never surfaced. The bitset kernel handles 216-bit outputs cheaply, so raising the threshold to 16 eliminates the cliff (that stratum: 38–45× → 1.12–1.38×) while leaving all other strata unchanged and all outputs bit-identical. Recommendation: make --cm-hybrid-threshold 16 the benchmark default; chart 2 above uses it, as the best honest configuration of both sides.

Fairness provenance (why these numbers can be trusted)

  • This audit found and fixed a comparator bug in the previous harness: the "Bitset" column at n≥18 was actually timing a recursive walk of CM's own DAG — 1.2–2.2× slower than a genuine flattened raw-AST Bitset. All published large-n ratios were re-issued against the corrected baseline, and every benchmark row now records bitset_baseline_kind so the baseline is auditable in the data.
  • Both sides received both optimizations (last-use memory freeing; numpy words engine), and comparisons are always engine-matched.
  • Correctness: 134,086,656 exhaustive rows across n=16–24 with zero failures on Python 3.13.5 (plus an independent 3.10.11 sweep); 2,909 additional adversarial checks with the memory-freeing branch force-enabled; suite at 159/159.
  • Variance is disclosed: large-n session CVs ran 7–16%; microsecond-scale reduced outputs are noisier (per-trial spread ~0.6–1.7), so medians are reported with ranges and the repr-3/4 trial mix.

Where the value of CMs actually lies

As computation: exact, compressed answers in the regime where the direct method cannot answer at all. Above n≈16 a full truth table is off the table; CM tracks the reduced problem, returns a 2live_k packed result plus its variable support, and refuses — explicitly and verifiably — when even the reduced output would exceed the safety bound. The audit confirmed the guard never wrongly accepted or refused across 6,000 sampled formulas.

As a compiler: the interned canonical DAG is a reusable intermediate representation. Semantic equality becomes pointer equality; common subexpressions are eliminated globally and for free; compiled programs and bound input templates persist across calls and across partial-input bindings; and the C1a lowering shows the IR admits progressively better backends (recursive → flat slots → vectorized words, 7× at n=24) without touching the semantics layer — each backend proven bit-identical. That separation — meaning fixed once, engines swappable underneath — is the compiler-shaped payoff, and it is exactly what made it safe to speed everything up by 2–7× this session without risking a single wrong bit.

What CM is not: a raw-speed win over a well-implemented Bitset on formulas that don't simplify. The kernel edge (~5–20%) is real but modest, and the wrapper gives it back on tiny outputs. Publications from this project state the claim as capability + exactness + structure at parity speed — not dominance.
